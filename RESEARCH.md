# Power Monitor Research

Research and design notes for `tauri-plugin-power-monitor`.

Research snapshot: September 2026.

> Research log for `tauri-plugin-power-monitor` — a Tauri v2 plugin that lets applications
> **observe** battery, power source, and sleep/wake state across Windows, macOS and Linux.
>
> These notes record the investigation and design decisions that informed the current
> implementation.

## Objective

Provide a single, idiomatic Tauri v2 abstraction that converts the native power-monitoring
mechanisms of Windows, macOS and Linux into one coherent query + event API for the
JavaScript/TypeScript frontend of a Tauri application — read-only, no power *control*.

## Tauri current state

- Tauri v2 is stable and actively developed. Current crates.io release at the time of
  research: `tauri` **2.11.x** (2.x line), `tauri-plugin` (build helper) **2.6.x**.
  The official plugins workspace pins `tauri = "2.10"` / `tauri-plugin = "2.5"` and MSRV
  **1.77.2** (see `plugins-workspace/Cargo.toml` @ `v2` branch). This is the
  upstream workspace baseline, not the current MSRV of this independent plugin;
  the dependency graph selected here currently requires Rust 1.88.
- Tauri v2 plugin architecture (verified against official plugins `global-shortcut`,
  `deep-link`, `cli`, `log`, `window-state`, `geolocation`):
  - `Builder::new("<plugin-name>").invoke_handler(tauri::generate_handler![...]).setup(...).build()` returning `TauriPlugin<R>`.
  - IPC commands are invoked from JS as `plugin:<plugin-name>|<snake_case_command>`.
  - Plugin → JS events use the `plugin-name://event-name` convention and are emitted
    from Rust with `app.emit(...)` (`use tauri::Emitter;`). Verified in `deep-link`:
    Rust emits `"deep-link://new-url"`, guest JS calls `listen('deep-link://new-url', ...)`.
  - State is stored via `app.manage(...)` in `.setup()`, exposed through an extension
    trait (`GlobalShortcutExt`-style pattern).
  - Permissions: handwritten `permissions/default.toml` + committed autogenerated files
    at `permissions/autogenerated/commands/<command>.toml` and
    `permissions/schemas/schema.json`, generated by `build.rs` via
    `tauri_plugin::Builder::new(COMMANDS).global_api_script_path("./api-iife.js").build()`.
  - Desktop-only plugins gate with `#![cfg(not(any(target_os = "android", target_os = "ios")))]`
    and `[target."cfg(...)".dependencies]`.
  - Guest JS is authored in `guest-js/index.ts`, built with rollup (shared config) into
    `dist-js/` + a committed `api-iife.js` global script; package name `@tauri-apps/plugin-<name>`.
- The plugins workspace already depends on **`zbus = "5.9"`** (workspace-level dependency),
  which sets precedent for D-Bus usage in official plugins.

## Electron comparison

Electron `powerMonitor` (verified against current docs):

| Electron capability | Windows | macOS | Linux | Relevance for Tauri plugin |
|---|---|---|---|---|
| `suspend` / `resume` events | ✓ | ✓ | ✓ | **In scope** — core of this plugin |
| `on-ac` / `on-battery` events | ✓ | ✓ | ✗ (docs: mac/win) | **In scope** — unified as `power-source-changed` |
| `isOnBatteryPower()` | ✓ | ✓ | ✓ | **In scope** — part of `get_power_state` |
| Battery level / charging | ✗ | ✗ | ✗ | **In scope** — Electron has *no* battery-level API in powerMonitor (open feature request since 2023; only `navigator.getBattery()` in renderer) |
| `shutdown` event | ✗ | ✓ (preventable) | ✓ (preventable) | Out of scope (control-adjacent; not a pure monitor event) |
| `lock-screen`/`unlock-screen` | ✓ | ✓ | ✓ | Out of scope for v1 |
| `getSystemIdleState` / `getSystemIdleTime` | ✓ | ✓ | ✓ | Out of scope for v1 (separate concern) |
| thermal-state / speed-limit (mac/win) | ✗ | ✓ | ✗ | Out of scope for v1 |

Design decisions informed by Electron: keep the event surface small and predictable
(`suspend`, `resume`, power-source change, battery change); do **not** copy Electron's
API shape blindly — Tauri has its own conventions (`UnlistenFn`, command + event naming).

## Platform APIs

Verified against primary sources (learn.microsoft.com, Apple headers fetched from
`apple-oss-distributions` mirrors, upower.freedesktop.org docs, kernel.org sysfs docs,
Chromium `base/power_monitor` reference implementation, zbus docs.rs).

### Windows

- **Query**: `GetSystemPowerStatus(&SYSTEM_POWER_STATUS)` (kernel32, `Win32::System::Power`):
  - `ACLineStatus`: `0` offline (battery), `1` online (AC), `255` unknown.
  - `BatteryFlag`: `1` high, `2` low, `4` critical, `8` charging, `128` no battery,
    `255` unknown; `0` normal (not a "no battery" indicator).
  - `BatteryLifePercent`: 0–100, `255` unknown.
  - `BatteryLifeTime` / `BatteryFullLifeTime`: seconds, `0xFFFFFFFF` (-1) unknown or on AC.
- **Events**: `WM_POWERBROADCAST` (536) delivered to a window's proc:
  - `PBT_APMSUSPEND` = 4 (0x4), `PBT_APMRESUMEAUTOMATIC` = 18 (0x12) — *always* sent on
    resume; `PBT_APMRESUMESUSPEND` = 7 is only sent additionally when caused by user
    input (Chromium ignores it; we do too, emitting exactly one resume event).
  - `PBT_APMPOWERSTATUSCHANGE` = 10 (0xA) — AC plugged/unplugged and status changes.
  - `PBT_POWERSETTINGCHANGE` = 32787 (0x8013) — with `RegisterPowerSettingNotification`:
    `GUID_BATTERY_PERCENTAGE_REMAINING {A7AD8041-B45A-4CAE-87A3-EECBB468A9E1}` (per-percent
    while discharging) and `GUID_ACDC_POWER_SOURCE {5D3E9A59-E9D5-4B00-A6BD-FF34FF516548}`.
- **Message-only windows (`HWND_MESSAGE`) do not receive broadcast messages** (MS docs) →
  the implementation must create a **hidden top-level `WS_POPUP` window** on a dedicated
  thread (the Chromium approach: `WS_EX_NOACTIVATE`, `WS_POPUP`, 0×0, never shown).
- **Modern Standby**: `RegisterSuspendResumeNotification(hwnd, DEVICE_NOTIFY_WINDOW_HANDLE)`
  is required to receive `PBT_APMSUSPEND` on machines with Modern Standby (Chromium comment).

### macOS

- **Query**: IOPowerSources (IOKit):
  - `IOPSCopyPowerSourcesInfo()` → blob; `IOPSCopyPowerSourcesList(blob)` → `CFArrayRef`;
    `IOPSGetPowerSourceDescription(blob, ps)` → `CFDictionaryRef`.
  - Keys (verified in `IOPSKeys.h`): `"Power Source State"` → `"AC Power"` / `"Battery
    Power"` / `"Off Line"`; `"Is Charging"` (bool); `"Is Present"` (bool);
    `"Current Capacity"` / `"Max Capacity"` (numbers; percent-based);
    `"Time to Empty"` / `"Time to Full Charge"` (**minutes**, signed int, `-1` = still
    calculating).
  - Release with `IOPSRelease(blob)`.
- **Power events**: `IOPSNotificationCreateRunLoopSource(callback, context)` → add to a
  `CFRunLoop` (fires on AC plug/unplug, battery changes, time-estimate updates).
- **Suspend/resume**: `IORegisterForSystemPower(refcon, &port, callback, &notifier)` (Apple
  QA1340 pattern; IOPMLib.h):
  - Callback `(refcon, service, messageType, messageArgument)`.
  - Message constants verified from xnu `IOMessage.h`: `kIOMessageCanSystemSleep` =
    `iokit_common_msg(0x270)`, `kIOMessageSystemWillSleep` = `iokit_common_msg(0x280)`,
    `kIOMessageSystemHasPoweredOn` = `iokit_common_msg(0x300)`,
    `kIOMessageSystemWillNotSleep` = `iokit_common_msg(0x290)`; with
    `sys_iokit = err_system(0x38) = 0xE0000000`, `sub_iokit_common = 0`.
  - `IOAllowPowerChange` **must** be called for `CanSystemSleep` and `SystemWillSleep`
    (otherwise sleep is delayed ~30 s); must NOT be called for wake messages.
  - Cleanup: `IODeregisterForSystemPower(&notifier)` → `IONotificationPortDestroy(port)` →
    `IOServiceClose(rootPort)` (mirrors Chromium `PlatformDestroy`).
  - We treat `kIOMessageSystemHasPoweredOn` (system fully awake) as **resume** —
    more accurate for applications than `WillPowerOn` (devices still unavailable).
- `NSWorkspaceWillSleepNotification`/`DidWake` (AppKit) exist as an alternative but require
  an ObjC runtime bridge; the IOKit C API achieves the same with zero extra dependencies.

### Linux

- **Primary**: UPower over D-Bus (`upower.freedesktop.org/docs/`):
  - `org.freedesktop.UPower` at `/org/freedesktop/UPower`: property `OnBattery` (bool).
  - `org.freedesktop.UPower.Device` at `/org/freedesktop/UPower/devices/DisplayDevice`
    (the sanctioned aggregate device): `Type` (u32; 2 = battery), `State` (u32:
    0 unknown, 1 charging, 2 discharging, 3 empty, 4 fully charged, 5 pending charge,
    6 pending discharge), `Percentage` (double), `IsPresent` (bool), `TimeToEmpty` /
    `TimeToFull` (int64 seconds, 0 = unknown).
  - Signals: `DeviceAdded`/`DeviceRemoved` on the daemon interface, and
    `org.freedesktop.DBus.Properties.PropertiesChanged` on devices (the legacy `Changed()`
    signal was **removed in UPower 1.90** — PropertiesChanged is the current mechanism).
- **Suspend/resume**: `org.freedesktop.login1.Manager` at `/org/freedesktop/login1`:
  `PrepareForSleep(bool start)` — `true` immediately before sleeping, `false` right after
  waking. No privileges required to subscribe. Unavailable on non-systemd systems →
  suspend/resume events are Linux-~ (documented limitation).
- **Fallback** (no D-Bus / no UPower, e.g. minimal headless servers):
  `/sys/class/power_supply/*` (kernel ABI, documented in
  `Documentation/ABI/testing/sysfs-class-power`): `type` (`Mains`/`Battery`),
  `online` (0/1, plus a PD-related `2` quirk on some kernels), `capacity` (0–100),
  `status` (`Charging`/`Discharging`/`Not charging`/`Full`/`Unknown`), `present` (0/1;
  file may be absent → kernel default present).
- **Rust D-Bus**: `zbus` (pure Rust, no C dependencies, already a workspace dependency of
  the official plugins workspace at 5.9). Blocking `SignalIterator` has no documented
  cancellation → the listener runs on a dedicated thread with
  `async_io::block_on` + `futures_util::select!` against an `event_listener::Event` stop
  signal, guaranteeing clean shutdown.

## Context and decisions

1. **No official plugin** exists for power monitoring in the reviewed official
  plugin list. Discussion #14543 remains open as a "Plugin Request" and frames
  the functionality at the plugin level.
2. The closest community plugin (`tauri-plugin-device-info`) polls battery state on
   Windows/Linux (polling is explicitly rejected as the primary mechanism for this plugin),
   has no suspend/resume and no AC events.
3. The other closest plugin (`tauri-plugin-idlemonitor`) has no battery/AC support and an
   unimplemented Windows suspend path.
4. No existing solution integrates with Tauri v2 permissions, event naming conventions,
   guest JS packaging, or lifecycle management at the quality bar of official plugins.
5. None of them model platform information gaps honestly (`Option<T>` for unknown values).

**Decision: Case C — a real need exists without an adequate implementation. The current
community implementation addresses that gap within the documented read-only scope.**

## Current implementation

`tauri-plugin-power-monitor` v0.1.0 — a **desktop-only, read-only** plugin:

- **1 IPC command**: `get_power_state()` → `PowerState { power_source, battery }`.
- **4 events** (Tauri `plugin-name://event` convention):
  `power-monitor://power-source-changed`, `power-monitor://battery-changed`,
  `power-monitor://suspend`, `power-monitor://resume`.
- Guest JS: `getPowerState`, `onPowerSourceChanged`, `onBatteryChanged`, `onSuspend`,
  `onResume` (each returning `UnlistenFn`).
- Architecture: native listeners **only signal** ("requery", suspend, resume) over an
  internal channel; a single dispatcher thread queries the backend, diffs against the
  last known state, and emits granular Tauri events (event-driven first; no polling).
- Platform backends: Windows (`GetSystemPowerStatus` + hidden `WS_POPUP` window +
  `RegisterSuspendResumeNotification`/`RegisterPowerSettingNotification`), macOS
  (IOPowerSources + `IORegisterForSystemPower` on an isolated CFRunLoop thread),
  Linux (UPower + login1 over zbus, with a documented sysfs fallback for queries).
- Explicitly **excluded**: shutdown/reboot/hibernate/sleep control, prevent-sleep,
  brightness, CPU governor, fan control, power policies (v1 is an observer only).

## Community context

- Matches the upstream discussion's plugin-level framing: the core feature request
  became a "Plugin Request" (#14542 → #14543), which is consistent with a community
  plugin approach.
- Electron parity gap: Electron ships `powerMonitor` in core; Tauri apps currently have
  no supported way to observe battery/AC/suspend state.
- It follows the established Tauri 2 conventions for structure, permissions, guest JS,
  packaging, and CI while remaining an independent community plugin.
